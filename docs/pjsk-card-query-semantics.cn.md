# Haruki-Cloud PJSK 卡牌查询语义整理

> 最后更新：2026-03-29
>
> 本文只整理这一轮已经落地的 `card/detail`、`card/list`、`card/image` 查询语义，不覆盖卡组、歌曲、教育、MySekai 等其他模块。

## 1. 文档目的

这一轮卡牌查询的主要目标有三点：

1. 让 `card/detail` 和 `card/list` 共用同一套入口分流规则。
2. 把“单张卡查询”和“多张卡筛选”明确拆开，避免命令语义混合。
3. 明确 `card/image` 不参与这次多卡筛选扩展，继续保持单卡定位语义。

## 2. 当前命令分流规则

相关入口文件：

1. `internal/pjsk/handler/sekai/card.go`
2. `internal/pjsk/render/card/parser.go`
3. `internal/pjsk/render/card/extractor.go`
4. `internal/pjsk/render/card/source_cloud.go`

当前 `card/detail` 与 `card/list` 的入口都走同一个分流函数：

1. 如果参数里带 `box` / `id` / `before` 这类卡牌一览附加标记，则转到 `card-box`
2. 否则，如果参数能被识别为“单张卡查询”，则转到 `card-detail`
3. 否则，按“多张卡筛选”处理，转到 `card-list`

也就是说：

1. `/查卡 1001` 会走 `card-detail`
2. `/查卡 mnr-1` 会走 `card-detail`
3. `/查卡 mnr 4星 fes` 会走 `card-list`
4. `/查卡 mnr 4星 id box before` 会优先走 `card-box`

## 3. 单张卡查询

单张卡查询当前只用于 `card/detail` 的自动分流，以及底层单卡定位逻辑。

### 3.1 支持的语法

当前明确支持两种写法：

1. 直接写卡牌 ID
2. `角色昵称 + 负数序号`

示例：

1. `1001`
2. `mnr-1`
3. `miku-2`

其中：

1. `1001` 表示直接查询卡牌 ID 为 `1001` 的卡
2. `mnr-1` 表示查询该角色最新一张卡
3. `miku-2` 表示查询该角色倒数第二张卡

### 3.2 当前限制

这里的第二种写法必须是“角色昵称后直接跟负数”：

1. `mnr-1` 可以
2. `mnr -1` 当前不作为同一语法保证
3. `mnr1` 不表示单张卡，而是会优先按箱活缩写类筛选语义处理

## 4. 多张卡筛选

多张卡筛选用于 `card/list`，以及 `/查卡` 在未命中单卡语义时的回退路径。

### 4.1 支持的筛选类型

当前已经落地的筛选字段有：

1. 角色昵称
2. 团体 / 纯团 / 混 VS
3. 稀有度
4. 属性
5. 技能类型
6. 卡池类型
7. 年份
8. 活动 ID
9. 箱活缩写

### 4.3 组合方式

这些筛选参数可以混合使用，当前以空格拼接为主。例如：

1. `miku 4星 蓝 fes`
2. `event123 mmjv 25年`
3. `mnr1 纯v 判分 蓝星`

当前实现会从同一串 query 中提取这些字段，并在数据库层与后置过滤里组合生效。

补充说明：

1. `生日` 在当前提取顺序里会优先被识别为生日稀有度，而不是单独的卡池类型筛选

### 4.4 当前边界

这一轮实现的是“固定字段提取 + 组合过滤”，不是自由自然语言理解，因此需要注意：

1. 最好使用已经约定好的短语和缩写
2. 未识别的自由文本不会自动变成复杂条件
3. 同类条件重复出现时，不保证有更复杂的优先级语义

## 5. `card/detail`、`card/list`、`card/image` 的区别

### 5.1 `card/detail`

`card/detail` 本质上是“单张卡详情”入口，但为了兼容 `/查卡` 的历史用法，现在会先做统一分流：

1. 单卡语义时返回 `card-detail`
2. 多卡语义时回退成 `card-list`
3. `box/id/before` 语义时转成 `card-box`

因此它现在更像“智能入口”。

### 5.2 `card/list`

`card/list` 虽然名字是列表，但为了避免两套语法分裂，也使用同一套入口分流：

1. 单卡语义时仍然返回 `card-detail`
2. 多卡语义时返回 `card-list`
3. `box/id/before` 语义时返回 `card-box`

这样 `card/detail` 和 `card/list` 两个入口的参数行为保持一致。

### 5.3 `card/image`

`card/image` 不参加这次多卡筛选扩展。

对外约定应保持为：

1. 只做单张卡定位
2. 调用方应传能够唯一定位卡牌的参数
3. 推荐直接使用卡牌 ID

需要特别注意：

1. 不要把 `角色 + 稀有度 + 属性 + fes` 这类多卡筛选参数传给 `card/image`
2. 不要把这次为 `card/detail` / `card/list` 增加的筛选语义视为 `card/image` 的能力
3. 即使底层单卡查询链未来还能兼容部分旧写法，`card/image` 的接口约定仍应以“唯一卡牌定位，优先卡牌 ID”为准

## 6. 入口帮助文本

当前 `card/detail` 与 `card/list` 的帮助文本已经同步为同一份说明，内容分为两段：

1. 查单张卡的方式
2. 查询多张卡牌的筛选参数

这份帮助文本的目的不是穷举所有实现细节，而是给用户一个最常用的输入范围。

## 7. 当前实现结论

这一轮卡牌查询语义可以概括为：

1. `card/detail` 和 `card/list` 共享分流规则
2. 单卡查询当前支持“卡牌 ID”与“角色昵称 + 负数序号”
3. 多卡筛选已经支持角色、团体、稀有度、属性、技能、卡池、年份、活动等组合条件
4. `card-box` 标记仍然拥有更高优先级
5. `card/image` 明确不扩展多卡筛选语义

## 8. 后续注意事项

如果后续继续改卡牌查询，建议遵守下面这几个原则：

1. 不要再让 `card/detail` 和 `card/list` 各自维护不同的参数语义
2. 新增卡牌筛选字段时，应同时补 `parser`、`extractor`、`source_cloud` 和测试
3. `card/image` 如果未来要扩展，也应先重新确认产品约定，不要直接复用多卡筛选语义
